## 1. 큰 그림 — 너의 세 가지 역할

우리 프로젝트에서 너는 **단순 조사 담당이 아님**. 데이터·시장·발표 세 축을 모두 다룬다.

| 영역 | 무엇을 | 왜 중요한가 |
|---|---|---|
| **A. 데이터** | 공개 IoT 데이터셋 발굴·다운로드·우리 도메인 매핑 제안 + Mock dataset 보강 | 박주상 ML 모델의 *재료*. 네가 raw 데이터를 깔끔하게 다듬어 넘겨야 박주상이 학습 가능 |
| **B. 시장** | 한국 시장·LG/삼성 사례·경쟁사 표를 *우리 슬라이드 형식* 으로 가공 | 발표 슬라이드 6~7 (시장·확장성) 의 메인 콘텐츠 |
| **C. 발표** | PPT 8슬라이드 리드 (스토리·디자인·전체 조립) | 발표 인상의 80% 결정 |

**핵심 원칙**: A·B 모두 *"raw → 정제 → 우리가 쓰기 좋은 형태"* 로 가공하는 것이 너의 진짜 역할. "조사만 하고 끝" 이 아님.

### 3.1 데이터 영역 — 박주상에게 넘길 자료 만들기

박주상이 ML 모델을 학습하려면 *깨끗하게 정리된 raw 데이터 + 우리 도메인 매핑* 이 필요. 네가 그 입력을 만든다.

**적합도 평가 기준** (★ 매길 때 참고):

#### 작업 D2 · 우리 도메인 매핑 제안서 (1.5시간)

박주상이 픽한 데이터셋의 **activity 라벨 → 우리 events.json 의 7개 이벤트** 매핑 제안서 작성.

**왜 너인가**: 박주상은 모델 코드에 집중. 도메인 매핑(어떤 활동이 어떤 이벤트인가) 은 *우리 events.json·rooms.json 을 가장 잘 이해하는 사람* 이 해야 함. 너는 사업계획서·시장 분석으로 우리 도메인 정의에 익숙해질 거라 적임.

**참고 파일**:
- `team-project-lg/backend/app/data/events.json` — 우리 7개 이벤트 정의
- `team-project-lg/backend/app/data/rooms.json` — 우리 5개 방 정의

**매핑 제안서 템플릿** (`docs/DATASET_MAPPING.md`):

```markdown
# 데이터셋 매핑 제안서

## 채택 데이터셋
- 이름: UCI ADL Recognition (Ordonez)
- 픽 사유: (박주상 의견)

## Activity → Event 매핑

| 원본 라벨 | 우리 event ID | 매핑 사유 | 자신도 (1~5) |
|---|---|---|:-:|
| Breakfast | post_cooking | 식사 직후 = 요리 직후로 일반화 | 4 |
| Lunch | post_cooking | 동일 | 4 |
| Sleeping | pre_sleep_30min | 취침 = 취침 임박 (시작 시점만 의미) | 3 |
| Leaving | going_out | 외출 | 5 |
| Returning | user_returned | 귀가 | 5 |
| Showering | (other) | 매핑 안 됨, 라벨 제외 | - |
| ... | ... | ... | ... |

## 매핑 안 되는 라벨
- 원본에는 있지만 우리 events 에 없는 것: Showering, Toileting, Spare_Time
- → ML 학습 시 "other" 통합 또는 제외 권장

## 우리 events 중 매핑 안 되는 것
- rain — 원본 데이터엔 날씨 정보 없음. ML 모델은 rain 제외하고 학습. 시뮬레이터에선 사용자 입력으로만.
- guest_arrival — 원본에 없음. 동일.

## 공간 매핑 (있는 경우)
| 원본 location | 우리 room_id |
|---|---|
| Kitchen | kitchen |
| Bedroom | bedroom |
| ... |
```

**산출물**: `team-project-lg/docs/DATASET_MAPPING.md`

**박주상에게 전달**: 작성 완료 → 박주상 검토 → 합의 후 확정.

#### 작업 D3 · Mock dataset v1 보강 (2시간, 멘토 피드백 후)

현재 Mock dataset (5방·7이벤트·4시나리오) 은 v1. **멘토 미팅 (5/16) 후 피드백을 반영해 보강**.

**보강 후보**:
- **이벤트 추가**: 멘토가 "이런 상황도 다뤄야 한다" 라 한 것 (예: 반려동물·물 흘림 등). 추가 시 `events.json` 에 새 항목 + 기존 시나리오에 영향 매핑 추가
- **시나리오 추가**: 4종 + 1~2개 추가 (예: "주말 청소 루틴", "외출 중 자동 청소"). `scenarios.json` 에 추가
- **공간 속성 보강**: 각 방에 *반려동물 출입·물 자주 흘림·아이방* 같은 속성 추가 가능
- **시간 정밀도**: 30분 단위 → 15분 단위 등

**작업 순서**:
1. 멘토 피드백 메모 정리 (미팅 후 30분 내)
2. 팀장과 상의 → "이건 v2 보강에 포함, 이건 백로그" 분류
3. `backend/app/data/events.json` / `scenarios.json` / `rooms.json` 편집 (JSON 형식 — 팀장이 형식 도와줌)
4. PR 또는 커밋 (팀장 도움)
5. 백엔드 골든 테스트 (`pytest`) 통과 확인 → 통과 안 하면 팀장이 룰 조정

**산출물**: 갱신된 JSON 파일들 + `docs/MOCK_DATA_CHANGELOG.md` (v1 → v2 변경 내역)

**팀장 협업 강도 높음**: 너는 데이터 내용을 결정, 팀장은 JSON 파일에 직접 반영·테스트.
